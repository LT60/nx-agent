# NX-Agent：让 Agent 操作 Siemens NX

把 Siemens NX 接入 Agent，让「自然语言需求 → 建模 → CAM 刀路 → 仿真验证」全程无鼠标完成。难点在于 NX 没有 Agent IDE 那套现成的运行反馈：写错了不会编译报错，改坏了不能 git 回滚，所以这些层都得自己造。

## 由什么组成

| 层 | 位置 | 做什么 |
|---|---|---|
| Agent 侧 | `mcp/` | MCP 服务端，19 个工具暴露给任意客户端 |
| 桥接层 | `bridge/` | 跑在 NX 进程内的 journal，文件队列收发指令 |
| 判据层 | `verify/` + `tools/` | nc_lint 静态体检、nc_diff 回归比对、.prt 快照回滚 |
| 部署 | `tools/start_bridge.py` | 一条命令拉起 NX + 桥接，自动处理启动同意框 |

真机验证：NX 2606 学生版，17 个真实加工操作、27 KB 截图、全流程零点击。API 查不到的地方，用 `nx_api_lookup` 检索本机 60 MB 的 NXOpen 文档。

---

## 一、为什么不能直接拿 Agent IDE 去套 NX

Agent IDE（Trae / Cursor / Codex 那一类）之所以能全自动，靠的是「**改代码 → 运行 → 测试自动报错 → git 回滚**」这四层白送的闭环，而 NX 这边只有第一层是白送的，另外三层必须自己造：

| 层 | Agent IDE | NX 现状 | 本仓库对应模块 |
|---|---|---|---|
| 写脚本 | 现成 | 现成（AI 会写 NXOpen / TCL） | — |
| 驱动 | 现成 | **缺** | `bridge/nx_bridge.py` |
| 验证 | 现成 | **缺**（没有“编译报错”这种东西） | `verify/nc_lint.py`（静态体检）+ `verify/nc_diff.py`（回归比对） |
| 回滚 | 现成 | **缺**（`.prt` 是二进制） | `tools/snapshot.py` |

补齐这三层 Agent 才能形成真正的闭环，**而这三层正是整套东西的全部价值所在**，不是“再找个更强的 Agent”能替代的。

## 二、架构

```
   用户开口（自然语言）
        │
        ▼
   ┌──────────────────┐
   │  Agent（任意 MCP  │   WorkBuddy / Codex / Claude Code / Reasonix
   │  客户端）         │   负责：理解意图、写脚本、看报错、自己改
   └────────┬─────────┘
            │ MCP (stdio / JSON-RPC)
            ▼
   ┌──────────────────┐
   │ mcp/server.py    │   把意图翻译成请求；校验类工作本地做掉
   └────────┬─────────┘
            │ 文件队列  queue/in  <>  queue/out
            ▼
   ┌──────────────────┐
   │ bridge/          │   跑在 NX 进程内，直接调 NXOpen
   │ nx_bridge.py     │
   └────────┬─────────┘
            │ NXOpen API
            ▼
        Siemens NX  ←→  .prt / 刀路 / NC 文件
            │
            ▼
   ┌──────────────────┐
   │ verify/nc_lint   │   上机前的强制关卡（静态体检）
   │ verify/nc_diff   │   改了后处理器之后，跟基准比对，自动分高危/低危
   │ tools/snapshot   │   改动前先拍照，出事就退回去
   └──────────────────┘
```

两个校验器都是「离线」的：它们只看纯文本，不需要 NX 在线、不需要机床、也不需要许可证，也就是说上机前能自动化掉的那一大半验证，全部落在这两个脚本里。

为什么用文件队列而不是 socket？因为跨机器共享盘也能用、企业网不用开端口（模具厂内网通常不给开）、NX 版本差异不影响传输层，而且每一笔请求都会在磁盘上留痕、出事能翻账。

## 四、快速开始

环境要求很简单：一台装有 NX（学生版即可） 的 Windows 64 位机器，加一个能跑 Python 的终端。NX 自带 Python 3.12，本项目所有脚本只用标准库，**不需要 pip 安装任何依赖**。

```bat
:: 1. 启动 NX 并挂上桥接（一条命令，自动处理启动时的同意框）
python tools\start_bridge.py

:: 2. 确认桥接真的活了（三项全 PASS 即通过）
python tools\bridge_probe.py

:: 3. 跑不需要 NX 的离线自检
python tools\selftest.py
```

启动脚本会在 12–16 秒内把 NX 拉起来并进入常驻轮询，**全程不需要点鼠标**。只想验证校验器而不装 NX 也可以，`nc_lint` 和 `nc_diff` 直接吃 `samples/` 里的样例文件即可。

学生版有三条硬限制（CAM 数据不能后处理、输出带水印、必须通过 SSC 客户端安装）、双实例并存的具体做法、以及各类故障处理，见 [`docs/部署指南.md`](docs/部署指南.md)。

## 五、开发循环：相当于网页开发的「刷新一下」

网页：改代码 → 刷新浏览器 → 人看 → 提要求 → 再改
**本项目**：改 journal / 改参数 → `nx_preview` → `preview_gallery.py` 出一页 HTML → 人看 → 提要求 → 再改

```
Agent 改完  →  nx_preview（重播刀路 + 3D 材料切除 + 每步截图）  →  state/preview/*.png
                                                                        ↓
             人说"这里多切了一刀"  ←  tools/preview_gallery.py 生成 HTML，浏览器打开
```

`nx_preview` 已经能跑了（2026-10-01 真机实测，0.2 秒返回）。
NX 没有“浏览器式的结果页”，所以自己做了 `tools/preview_gallery.py`：
把每次预览的图按时间排成一页，带时间戳和步骤标签（刀路重播 / 3D 切除 / 当前视图）。

> ⚠️ 实测踩到的一个会把桥接搞死的坑：对**没生成刀路**的操作调重播，
> NX 会弹模态框 → journal 卡在主线程 → 桥接心跳停 91 秒，连 stop 都投不进去，只能杀进程。
> 现在 `preview` 会先用 `AskPathExists()` 过滤，没刀路就只截当前视图并说明原因。

### 「操作软件」这一步跳不跳得过？

**启动那一步：已经跳过了**（`ugraf.exe -auto=`，零点击）。
**运行期间的弹窗：跳不过** —— 这是 NX 的架构约束（图形界面单线程，journal 跑在主线程，
已查证 NXOpen 里没有定时器/回调可以绕开）。

但正确应对不是“绕过弹窗”，而是**在软件外面盯着它**：

```bat
python tools\dialog_sweeper.py --once     :: 诊断：现在屏幕上有什么模态框
python tools\dialog_sweeper.py --watch    :: 常驻清扫（桥接开着时另开一个窗口跑）
python tools\dialog_sweeper.py --log      :: 看历史：都弹过什么、怎么处理的
```

原理：**NX 内部的代码救不了自己**（它正在等那个框），但**外部进程可以**——
卡住的只是 NX 的主线程，Windows 上别的进程照样能枚举它的窗口、按下按钮。
安全策略：已知弹窗选保守项（遥测→Decline，是否保存→No）；
未知弹窗绝不乱点，只记录并告警；只剩“同意/覆盖”这类按钮时不动。全程留痕。

## 六、自主性是怎么长出来的

整套设计只围绕一句话展开：**别让 AI 猜 NXOpen，让 AI 改已经跑通过的代码。**

```
用户提需求  →  Agent 写代码试跑  →  照真实报错改  →  跑通入库  →  下次直接调用
                    ▲                                            │
                    └────────── 失败就把原始报错回传 ─────────────┘
```

Agent 拿到需求后的动作是固定的：先查 `nx_api_lookup` 确认函数签名；遇到不熟的接口就在 NX 里反射 `fn.__doc__` 拿到完整参数表；然后写一个最小 journal 试跑一次并照真实报错修正。跑通即入库，下次同类任务直接调用，而且可以参数化和批量循环。 每跑通一次能力库就厚一层，这是唯一能持续积累的路径。

需要说清楚的是：本项目所有已验证的能力都是直接写 API 写出来的，一次录制都没用过，包括建方块、改尺寸、加放电头、生成刀路、3D 切除仿真和导出刀路数据。录制只在「API 查不到、文档也没有」的极少数角落才有兜底价值，不该被写进前置条件。用网页开发类比就很清楚：写页面的时侯没有人会先去录一遍鼠标操作。

### 真正拿不到的是工艺参数，而那是问来的

参数从来不是卡点，因为三条路都拿得到：**交互式问**最简单，Agent 对话本身就是通道，它可以直接问转速多少、几齿、留多少余量，然后把回答填进下一轮，这条现在就能用。**留空**走 NX 模板自带的默认值，**凭通用知识定初值**则和网页 Agent 先给 `padding: 16px` 是同一个打法，已落地为 `config/cutting_defaults.json` 加 MCP 工具 `nx_suggest_params`：按材料、刀具、工序算出转速进给切深，并附一份「该问操作者哪几句话」的清单。

因此录制的真实价值是让「第一轮就接近正确」成为可能，而不是「没有就干不了」。真正的硬约束只有一条：**改错了要多久才发现**。网页刷新一下就知道，CAM 得上机床才知道，所以这条循环必须靠离线判据（`nc_validate` 与 `nc_diff`）撑住，而不能指望参数一开始就对。

## 七、安全边界（不可协商）

| 环节 | 谁负责 |
|---|---|
| 写脚本、改参数、批量出文件 | Agent |
| 生成刀路、出 NC | Agent（在 NX 里算） |
| **G 代码上机前的体检** | `nc_lint.py`，不通过就不许出 |
| **改了后处理器的回归比对** | `nc_diff.py`，出现高危差异就不许上机 |
| **仿真 + 机床空运行** | 人 |
| **工艺决策、余量、装夹、签字** | 人 |

最容易出隐蔽错误的一步是改后处理器：操作者往往以为只加了注释而实际动了进给。`nc_diff.py` 把这类改动变成纯文本回归测试，不上机床就能拦住。细节见 `docs/模拟能替代多少真机.md`。

自动化上限给的是现实值而不是营销值：

| 任务类型 | 能做到 | 备注 |
|---|---|---|
| 程序单 / 电极清单 / 工艺卡 | ~95% | 纯文本，风险为零 |
| 批量后处理 / 出图 / 归档 | ~90% | 批量循环骨架已备（`templates/electrode_batch.py`） |
| 标准件、电极等规则化建模 | ~80% | 规则越明确越高 |
| 刀路策略生成 | ~65% | 必须人审，必须仿真 |
| **工艺决策与责任签字** | **0%** | 不由 Agent 承担，一块模料报废够做几百次手工 |

## 八、已验证 / 未验证

**不需要 NX 就能跑的部分**：MCP 协议握手与全部 19 个工具、`nc_lint` 全流程（能准确抓出样例里的 7 个问题）、`nc_diff` 分级（把 2 处高危差异与 2 处低危差异分开，高危时返回 `isError` 直接拦住上机）、队列往返、桥接离线时立即报错而不是干等、超时之后先判清「没送达」还是「已在跑」再决定要不要重试、写路径限制在工作区内、结构化错误回传、`.prt` 快照与回滚、过期请求隔离，`tools/selftest.py` 全项通过（27 项；其中 5 项要读本机装配实验产物，产物不在时记为「跳过」而不是失败）。

**需要真机 NX 的部分**：在 NX 2606 学生版上跑通了启动（12–16 秒就绪、零点击）、`ping` 往返 1.35 秒、从 `mill_planar.prt` 模板新建工作部件、从模板枚举出 **17 个真实加工操作**、截图写出 27 KB PNG、保存部件成功。

**还没验证的**：学生版能否真的后处理出 NC（官方说不支持，但相关接口都在，值得拿带真实刀路的部件试一次）；桥接连续常驻数小时的稳定性；`GenerateToolPath` 在带几何的真实部件上跑通「生成 → 后处理」的完整链路。

API 参数踩坑、三条驱动死路的证据、授权机制与弹窗处理这些技术细节，见 [`docs/技术验证记录.md`](docs/技术验证记录.md)。

## 九、社区已有的 NX MCP 项目，为什么不直接换

社区确实有现成方案，其中有一个质量相当高：

| 项目 | 干什么 | 对本场景的适配度 |
|---|---|---|
| **`DreamEnding/NX_MCP`**（96★，MIT，活跃维护） | 外部 Python sidecar（FastMCP / MCP SDK v2）加 NX 内 journal bridge（127.0.0.1 + 256-bit token 认证），默认 16 个工具 | 架构**跟本项目独立得出的结论一致**（外部进程加 NX 内 journal），算一次交叉验证。但它的 bridge 官方启动方式是 `run_journal.exe`，在学生版上固定报 3615094 直接跑不起来；工具面是**纯 CAD 建模**（草图、拉伸、装配、制图、测量、STEP），**零 CAM**；它也没有判据层（`nc_lint` / `nc_diff`）与回滚层 |
| **`mingfeng6684/nxopen-mcp`** | 不驱动 NX，只给 agent 提供 **NXOpen API 知识检索**（BGE-M3 + sqlite-vec，从本机安装的 NX 抽取文档建索引） | 思路**完全对**，代价是要下几百 MB 嵌入模型。而本机本来就带着同一份原始文档（`NXBIN\managed\NXOpen.xml`，60 MB / 14 万条成员），直接做文本检索更快更准，已做成 `tools/nx_api_lookup.py` 与 MCP 工具 `nx_api_lookup` |
| **`TQJ2007-git/nx-mcp`** | 目标是实时模式（HTTP 加 NX 内 journal server），但**当前只有批量模式**，即直接 `run_journal.exe` 跑脚本 | 学生版上直接死（3615094） |

结论是不换，但吸收。不换的原因是本项目要解决「CAM + 判据 + 回滚」而社区方案解决「CAD 建模」，交集只有建模那一块；学生版的驱动入口是 `-auto=`，而它们的官方路径是 `run_journal.exe`。值得抄的工程实践有五条：**workspace 禁闭**（文件参数限制在工作区内，穿越与绝对路径一律拒绝）、**失败即回滚加 undo mark**、**超时语义区分**（`not_started` 与 `unknown` 分开，不确定执行绝不重放）、**real-NX 验收门**（真机跑过才算发布门槛）、以及 **API 知识检索**。

这五条目前的状态分开说，免得读起来像已经全有了：**路径边界已落地**，但边界划在「谁决定放哪」上而不是「写还是读」上 —— 预览图、快照、JSON 报告这类程序自己决定位置的运行时产物必须落在仓库内（要放宽就设 `NX_AGENT_ALLOW_OUTSIDE=1`），而 NC 输出目录、新建部件落点这类人指定的业务目的地原样放行，因为一律禁闭会把「把程序输出到我的加工目录」这个核心用法挡死；读取侧刻意不锁，打开用户自己的 `.prt` 是正常用法，而服务端本来就跑在用户自己的机器上，锁读取不会更安全。**超时语义已落地**，桥接在动手前先写一笔 `running` 占位，于是超时之后能分开四种情形：跑完了只是服务端等超了（当成功返回）、已开跑没跑完（禁止重放）、还在队列没人认领（撤销它，可以安全重试）、被取走却没留结果（禁止重放）。**API 检索**由 `nx_api_lookup` 承担。**回滚**是快照级的（`tools/snapshot.py`，每次独立留档、回滚前先把现状再存一份），NX 原生的 undo mark 没有用。**real-NX 验收门**还只是流程约定，没有做成硬门禁。

### 写 NXOpen 代码之前先确认函数签名

```bat
python tools\nx_api_lookup.py --limit 4 --summary Postprocess
```

```
[方法] NXOpen.CAM.CAMSetup.Postprocess(NXOpen.CAM.CAMObject[],System.String,System.String,NXOpen.CAM.CAMSetup.OutputUnits)
     Postprocess
     Created in NX4.0.0 License requirements: cam_base ("CAM BASE")
```

MCP 里也有同名工具 `nx_api_lookup`，Agent 写任何 NXOpen 代码之前都应该先调它。这个工具要是不存在，下面四个坑一个都避不开：

```
CAMSetup 上没有 GetOperations（GetOperations 在 CAMFeature 上）
Postprocess 是 4 参不是 3 参
UF.Disp.CreateImage 已被删除（现用 Views.CreateImageExportBuilder）
part.CAMSetup 无 CAM 设置时抛异常而非返回 None
```

（`--class CAMSetup` 可以列全部成员；首次建索引约 4 秒，之后走缓存 0.4 秒。）

## 十、为什么「只装 MCP」不够

常见误解是把全自动的缺口理解成「缺个 MCP」，实际上缺口有四块而 MCP 只解决第一块：

| 缺口 | 谁来解 | 现状 |
|---|---|---|
| 1. 通道：Agent 怎么把指令递进去 | MCP + 文件队列 | 本仓库已提供（`mcp/` + `bridge/`） |
| 2. 能力：怎么可靠地把活干成一件事 | 见下方三层模型 | **Agent 直接写 + 沉淀成封装** |
| 3. **判据：Agent 怎么知道这次做对了** | 只能自建（`nc_lint` + `nc_diff` + 几何算法） | **最难，且无现成方案** |
| 4. 回滚：做错了怎么退回去 | `tools/snapshot.py` | 已提供 |

判断标准只有一句：**Agent 能不能自己发现「这次做错了」？** 不能的话那不是全自动，只是自动执行了一次。

### 更准确的说法是缺标准库，不是缺能力

NX 的原语其实是全的：`CreateBlockFeatureBuilder`、`GenerateToolPath` 这类单个函数由软件白送，几千个都在 NX Open 里。缺的是上面两层。**编排**是把一串原语按正确顺序和上下文拼成「干成一件事」，这部分 Agent 直接写；**能力封装**要带命名、参数、前置检查与后置校验，可安全反复调用，这部分必须自己造。

录制能录到一次编排快照，但编排本身 AI 写得出来：找特征、建 builder、设几何、布尔求和、提交，这一串「加放电头」的编排 Agent 一次写对，没看任何录制。录下来的代码参数写死、对象引用也写死，要变成可复用能力必须参数化、泛化并加校验。

用编译器类比最贴切：**NX 有 syscall，但没有 stdlib，也没有包管理器。** 一段 journal 相当于一次 strace 记录，你要造的是 `create_electrode(name, x, y, z, stock)` 这样的库函数。

原语多不等于能力够。**调原语必须知道模型当前的确切状态**（有没有 work part、布尔运算的 target 是谁、有没有激活的草图），人靠眼睛看对话框就知道而 Agent 必须自己查，所以需要 `probe` 和 `part_info` 这类读状态的工具。**原语的报错是写给程序员看的**：「Boolean operation failed」不说明原因也不指出下一步，所以回传给 Agent 的必须是原始 traceback 加完整上下文。**原语没有业务语义**：「做这个电极」在 API 眼里是几十个原语调用。

### 判据：算法为主，视觉为辅

G 代码的判据是纯算法问题而不用视觉：坐标越界、安全平面下快速移动、转速进给越界、刀补未取消都是符号级确定性判断，`verify/nc_lint.py` 已实现。3D 模型分两类：**算法可判**的是几何度量（尺寸、壁厚、包围盒、体积）、拓扑（是否封闭实体、破面、自相交）、刀路扫掠体与模型的布尔差集以及干涉体积，精确且可复现；**视觉可判**的只有图不像、曲面不顺、外观缺陷这类，粗且不稳定。

判据必须确定性。视觉模型的判断不可复现，同一条刀路问两次可能给出不同结论；Agent 的自治循环靠反馈信号收敛，判据一旦随机循环就退化成随机游走。**把确定性的几何问题交给概率模型判断，是把问题降级。** 判断「这把刀会不会切到不该切的地方」的正解是把刀具体沿刀路扫出的体与模型求布尔交，交集体积大于零即干涉，答案精确到浮点且完全可复现；让视觉模型看渲染图，得到的只是一句「看起来可能有风险」。所以视觉用来给人看、用来发现明显异常，不做判据主体。

### 三个瓶颈

**没有客观对错判据**最严重：浏览器里对错有客观答案（DOM 变了没、测试过没过、console 报错没），3D 里「这刀路对不对」却取决于材料、机床、装夹和师傅经验。这是本质困难而非技术问题。**看不见摸不着几何**排第二但可部分解决：正解不是给它看图，而是把几何转成数字（包围盒、体积、最小壁厚、孔位坐标、干涉结果、过切欠切余量），这些数字比看图可靠得多。**反馈太慢**排第三：改一次刀路要算几十秒到几分钟、跑仿真更久，迭代循环被拉长，时间和 token 成本都高。

由此得到一条可操作的分界线：**能用数字判的**（干涉、余量、行程超限、转速进给越界、刀具碰撞）可以做全自动；**只能靠眼睛判的**（曲面质量、外观、分型面顺不顺）永远需要人。程序单、批量后处理、规则化建模在数字可判这一侧，曲面质量评估在另一侧。

## 十一、「真机跑」能模拟掉多少？

结论先说：**能模拟掉一大半，但删不掉最后一步**，把「真机跑」拆成五层来看：

| 层 | 在验证什么 | 本仓库能否覆盖 |
|---|---|---|
| ① 语法与安全规则 | 少小数点、缺 M30、S/F 越界、行程超限 | ✅ `nc_lint.py` |
| ② 后处理器改动的影响面 | 这次改 `.tcl` 到底动了哪里 | ✅ `nc_diff.py` |
| ③ 刀路几何 | 该切的切没切掉、撞不撞夹具 | ⚠️ 靠 NX 内置仿真，**但它看不见后处理器** |
| ④ G 代码在特定控制器下的行为 | 控制器认不认、偏置对不对、换刀时序 | ❌ 要 VERICUT / NCSIMUL 这类，很贵 |
| ⑤ 机床物理现实 | 反向间隙、伺服跟随误差、热变形、装夹变形 | ❌ **只能真机** |

有三个容易反直觉的点必须记住。**NX 内置仿真看不到后处理器**，因为它仿的是内部刀路数据而不是后处理之后的 G 代码，所以后处理器写错了仿真照样显示正常，第 ② 层必须自己补。**仿真器只是模拟控制器的解析器而不是在运行它**，也就是官方那句「Even an external G-code simulator models the controller's parser; it does not run it.」，因此第 ④ 层永远有道缝。**同一型号不同序列号的机床后处理器都要分开维护**，因为调机参数不同，这恰好说明第 ⑤ 层为什么模拟不掉：要验证的东西压根没进模型。

模拟能把上机次数从「每次改都上机」压到「只有首次和关键变更才上机」，但上机这一步删不掉，完整论证与一次具体案例见 `docs/模拟能替代多少真机.md`。
